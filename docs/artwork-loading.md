# 封面显示与长时间播放

## 上游方法

2026-11-12 核对 `egoist/mygo-music` 的 `main`，提交
`552e25c04023aa00c551d77db69aaab16f60bf2d`：

- `internal/music/fetch.go` 用 Go 获取图片，应用图片专用请求头；`SizedImage`
  填充 URL 的 `{size}` 占位，并在跳转到其它主机时限制凭证转发。
- `internal/app/artwork.go` 在后台获取、解码和缩小封面，再通过 `ui.Bitmap`
  交给原生 UI 绘制。内存缓存上限为 64 MiB，超过后按最近使用顺序淘汰到 75%。
  最多 8 个并发加载任务，另有解码像素预算；同时请求同一原图时共享下载。
- `internal/app/ui_nowplaying.go` 为播放页请求 600 像素封面并保留当前引用。
  原生封面路径没有本项目此前的 30 分钟 HTTP 租约。

这是上游的原生渲染与内存缓存机制，不能据此声称当前 WebView 项目也实现了
相同的位图、背景处理或 64 MiB 图片字节缓存。

## 本项目复现

旧浏览器实例中，多组正在播放的队列封面返回 HTTP 410；对同一歌曲重新读取
专辑后，新封面地址返回 200、`image/jpg`（66,633 字节）。这说明至少有一条
已复现的故障来自本地图片租约，而非源站没有封面。SHIELD 旧 APK 的只读截图
也显示了破图，但本次没有读取其内部 HTTP 状态，不能将真机故障原因完全等同。

此前 `Server.images()` 把封面放入 30 分钟过期的通用媒体租约。队列寿命更长，
播放页重新打开时，旧图片地址已失效；前端又没有破图回退。

## 本次处理

- 图片地址与音频租期分开：图片地址在进程内按最近使用顺序淘汰，登记项仍有
  1,500 上限，当前歌曲封面受保护；图片密集浏览优先淘汰其它图片。
- 后续队列项目的封面若已淘汰，开始播放它时从保留的原始地址重新登记。
  重启仍沿用原有的原始地址持久化和重新代理机制。
- 图片在请求时取得当前插件图片头，保持跳转凭证隔离；音频的到期、撤销和
  Range 行为保持原合同。
- 播放页大封面和底部小封面加载失败时显示 SVG 占位，每个元素最多额外重试
  两次。旧歌曲／已移除元素的回调不修改新封面，不重启音频，不改变焦点。

这里实现的是有上限的图片地址登记，不是图片字节或磁盘缓存。旧页面中已经
不存在的进程内地址不能跨核心进程复用；重新加载页面后使用当前核心的新地址。
回归在 `core/internal/server/artwork_test.go`、`tests/artwork.spec.cjs`；
真机新 APK 的验证须在下一次明确要求的签名发布后进行。
